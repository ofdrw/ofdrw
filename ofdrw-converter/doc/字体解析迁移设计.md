# OFD 字体解析能力评估与模块迁移设计

> 状态：待评审（本文档仅描述设计与方案，**不含任何代码改动**）
> 关联模块：`ofdrw-converter`、`ofdrw-font`
> 背景：为 CanvasImageExporter 的渲染正确性，评估字体解析能力现状，并规划字体解析代码向 `ofdrw-font` 模块迁移

---

## 1. 背景

CanvasImageExporter 的渲染质量直接依赖字体解析能力。在实际 OFD 文档中，文字定位大量依赖字形索引（GID）而非 Unicode，且内嵌字体常为裁剪字体（缺少部分表）。本文件评估：

1. 现有字体解析在 GID 场景下的能力边界。
2. 因为字体解析能力缺失导致的具体渲染缺陷。
3. 字体解析代码迁移到 `ofdrw-font` 模块的方案与取舍。

---

## 2. 现有能力评估

### 2.1 代码结构

字体解析代码位于 `org.ofdrw.converter.font`，共 20 个类、约 4240 行：

| 类别 | 类 |
| --- | --- |
| 核心解析 | `TrueTypeFont`、`TTFDataStream`、`MemoryTTFDataStream`、`TrueTypeCollection` |
| 字形数据 | `GlyphData`、`GlyphDataProvider`、`FontDrawPathProvider`、`GlyphRenderer` |
| 字形轮廓 | `GlyfDescript`、`GlyfSimpleDescript`、`GlyfCompositeDescript`、`GlyfCompositeComp` |
| 字符映射 | `CmapSubtable` |
| 度量与命名 | `HorizontalHeaderTable`、`HorizontalMetricsTable`、`NamingTable`、`NameRecord` |
| 包装 | `FontWrapper`、`PdfFontWrapper` |
| Type1 | `type1/Type1SegSplitParser` |

该实现裁剪自 PDFBox 的字形解析部分，外部依赖为 `org.apache.fontbox.*`、`org.apache.commons.io.IOUtils`、`org.slf4j.*`。

### 2.2 能力结论

| 能力 | 现状 | 依据 |
| --- | --- | --- |
| 按 GID 取字形轮廓 | ✅ 支持 | `TrueTypeFont.getGlyph(int)` / `getPath(int)` |
| 复合字形递归解析 | ✅ 支持 | `getGlyphData` 内 `description.resolve()` |
| OpenType/CFF 按 GID 取路径 | ✅ 支持 | `cffFont.getType2CharString(gid)` |
| Type1 字体 | ✅ 支持 | `Type1SegSplitParser` |
| 裁剪字体（仅 head/maxp/loca/glyf） | ✅ 支持 | 与 `font/README.md` 声明一致 |
| cmap 子表格式覆盖 | ✅ 支持 0/2/4/6/8/10/12/13/14 | `CmapSubtable.initSubtable` |
| `Glyphs` 一对多映射 | ✅ 按 glyphCount 展开 | `AWTMaker.writeText` |
| 缺 cmap 时按 GID 渲染 | ✅ 可用 | 实测 `font_10.ttf`（无 cmap）gid=469 可正常取到 2 个轮廓 |
| 字体替换后 GID 正确性 | ❌ 不正确 | 见 3.1 |
| GID 越界容错 | ❌ 抛 NPE | 见 3.2 |
| CFF 越界检查 | ❌ 缺失 | 见 3.3 |
| 缺必需表时的降级 | ❌ 异常穿透 | 见 3.4 |
| CFF2 / 可变字体 | ❌ 不支持 | 见 3.5 |
| `hmtx` 宽度的使用 | ❌ 仅用于 leftSideBearing | 见 3.6 |

### 2.3 实测数据

对测试资源 `font_10.ttf`（11 张表，**无 cmap**）的实测：

| GID | 结果 |
| --- | --- |
| 0 | 空字形（无 cmap 时 `getUnicodeGlyph` 的兜底值） |
| 469 | 2 个轮廓，正常 |
| 470 | 空字形（合法但无轮廓） |
| 8112（越界） | `getGlyph` 返回 null，`getPath` 抛 NPE |

结论：**“缺表 + 仅有 GID”这一组合本身可以正确渲染**，设计上已预判到该场景。问题集中在字体替换后的 GID 失效、以及异常容错不足。

### 2.4 真实样本集分析

对 58 组真实 OFD 样本（配套 PDF 用于交叉核对）的字体普查：

**格式与表结构分布**（共 59 个内嵌字体文件）：

| 格式 / 表组合 | 数量 | 当前代码 |
| --- | --- | --- |
| TrueType sfnt `0x00010000`，含 head+maxp+loca+glyf+**cmap**+hmtx | 35 | ✅ 可处理 |
| TrueType sfnt `0x00010000`，含 head+maxp+loca+glyf+hmtx（**缺 cmap**） | 19 | ✅ 按 GID 可渲染 |
| sfnt 版本 `0x74727565`（“true”） | 5 | ❌ 无法识别 |
| 裸 CFF `0x01000402` | 4 | ❌ 无法识别 |
| 裸 CFF `0x01000403` | 1 | ❌ 无法识别 |

**关键观察**：

1. **缺 cmap 是常态而非例外**：19/54 的 TrueType 字体无 cmap，占约 35%，涉及 6 个文档（`doc1File.ofd`、`signout.ofd`、`testImageNotFound.ofd`、`testPathClip.ofd`、`zsbk.ofd`、`文字横向-数科.ofd`）。这类文档只能按 GID 渲染，因此 §3.1 的“字体替换后 GID 错乱”属于**高频风险**，且因缺 cmap 无法用 Unicode 兜底。
2. **三种格式解析器完全无法识别**：
   - `0x74727565`（“true”）是合法的 TrueType sfnt 版本标记，`head` 版本为 `0x00010000`、`numGlyphs=36984`、`loca` 长度校验通过，仅因魔法值不同被误判
   - 裸 CFF（`0x01000402` / `0x01000403`）为 CFF 头部 `major=1, minor=0, hdrSize=4, offSize=2`，后接 Name INDEX，可正确读出字体名（如 `UCTIWJ+MinionPro-Regular`、`FXBMIR+HiraginoSansGB-W6`）；当前代码会把它当作 sfnt 表目录读取，必然失败
   - `intro-数科.ofd`（42 页）单文档内同时存在上述三种格式
3. **`hmtx` 覆盖完整**：所有字体均带 `hmtx`，§4.6 的步进兜底具备数据基础。

## 3. 缺陷清单

### 3.1 字体替换后 GID 语义错乱（严重）

`FontLoader.loadFontSimilar` 的降级链路为：内嵌字体 → 相似字体替换 → 默认字体兜底。

一旦走到后两步，新字体的 GID 空间与原文档字体不同，而 `AWTMaker.writeText` 的 `CGTransform` 分支**无条件按原 GID 取轮廓**：

```java
GeneralPath drawPath = typeFont.getPath(gid);   // 字体已替换，GID 已失去原有含义
```

对比 Unicode 分支是安全的（走 cmap 重映射，换字体不影响）。`FontWrapper` 已携带 `isEnableSimilarFontReplace` 标志，但 `AWTMaker` 未使用。

**后果**：输出字形错乱，且无任何报错或日志。

### 3.2 GID 越界导致 NPE（严重）

```java
public GlyphData getGlyph(int gid) {
    if (gid < 0 || gid >= numGlyphs) return null;
}
public GeneralPath getPath(int gid) {
    return getGlyph(gid).getPath();   // 未判空
}
```

`AWTMaker` 中该处只 `catch (IOException)`，NPE 会穿透到 `writeContent` 的 `catch (Exception)`，导致**整个 PageBlock 渲染失败**，一个坏 GID 可连带整段文字丢失。

### 3.3 CFF 分支缺少越界检查

```java
if (this.cffFont != null) {
    Type2CharString cs = this.cffFont.getType2CharString(gid);   // 未校验 numGlyphs
    return cs != null ? cs.getPath() : null;
}
```

与 TrueType 分支行为不一致。

### 3.4 缺必需表时异常穿透

缺 `head`/`maxp`/`loca`/`glyf` 任一时，解析器抛出 `IllegalArgumentException`（RuntimeException）。而 `FontLoader.loadExternalFont` 只捕获 `IOException`：

```java
} catch (IOException e) { ... }
```

异常会穿透，虽被上层 `catch (Exception)` 兜底，但结果仍是字体被替换为默认字体，从而触发 3.1。

### 3.5 不支持 CFF2

全文无 `CFF2` 支持。`.otf` 中若为 CFF2 表（可变字体常用），`tables.containsKey("CFF ")` 为 false，最终抛出“没有 glyf 表”，字体整体加载失败。

### 3.6 `hmtx` 仅用于左边距

`HorizontalMetricsTable.getAdvanceWidth` 虽已实现，但 `TrueTypeFont` 仅使用 `getLeftSideBearing`，且 CFF 分支根本不读取 `hmtx`。当 `DeltaX` 缺失时，字符步进会失真。

## 4. 修复方案

### 4.1 GID 失效时的行为

**决策：跳过该段字形，只告警。**

字体被替换后不再按原 GID 取字形，跳过并记录 warn 日志。理由：避免输出可见的错误字符；该段文字不显示优于显示错误内容。

### 4.2 GID 越界时的行为

**决策：跳过该字形，其余文字正常渲染。**

- `getPath` 补判空，返回 null
- `AWTMaker` 的 catch 由 `IOException` 放宽到 `Exception`，并判 `drawPath == null`

### 4.3 缺表时的降级

**决策：换用相似字体 + 输出告警。**

- `loadExternalFont` 的 catch 放宽到 `Exception`
- 字体替换时记录 warn 日志

### 4.4 告警输出

**决策：仅写入日志（slf4j）。**

不改变公开 API，不引入告警结果类。

### 4.5 CFF 越界

**决策：补上 `numGlyphs` 越界检查**，与 TrueType 分支对齐。

### 4.6 字体格式识别

**决策：纳入本期修复。**

在 `TrueTypeFont.parse(TTFDataStream)` 的格式识别处补充以下分支：

| 首 4 字节 | 格式 | 处理 |
| --- | --- | --- |
| `0x00010000` | TrueType sfnt | 现状 |
| `0x74727565`（“true”） | TrueType sfnt | **按 sfnt 解析**，与 `0x00010000` 同一路径 |
| `0x4F54544F`（“OTTO”） | OpenType sfnt | 现状（经表目录判断 `CFF `） |
| `0x01000402` / `0x01000403` | 裸 CFF 数据 | **直接交给 `CFFParser`**，跳过 sfnt 表目录读取 |
| `0x0001 0x0000` / `0x74746366` | TTC | 现状（`TrueTypeCollection`） |
| `0x8001` / `%!` | Type1 | 现状（仅识别，本期不接入渲染） |

裸 CFF 的处理要点：

- 裸 CFF 无 `head` 表，`unitsPerEm` 与 `numGlyphs` 无法从 sfnt 表读取，需从 CFF 的 `Top DICT`（`FontMatrix`、`CharStrings INDEX`）获取。
- 参考现有 CFF 分支：`getFontMatrix()` 已对 `cffFont != null` 使用 `cffFont.getFontMatrix()`，可复用。
- 当前代码在无 `head` 表时会尝试用 `CFFParser` 解析整个字节流，**理论上已覆盖裸 CFF**，但因先读取 `numberOfTables` 并遍历表目录而失败。修复方式是**在读取表目录之前先做魔法值判断**。

### 4.7 修复优先级

| 优先级 | 改动 | 影响面 |
| --- | --- | --- |
| P0 | `getPath` 补判空 | `TrueTypeFont` |
| P0 | `AWTMaker` GID 分支放宽 catch + 判空 | `AWTMaker` |
| P0 | 字体替换后跳过 GID 分支并告警 | `AWTMaker` |
| P0 | `loadExternalFont` 放宽 catch | `FontLoader` |
| P0 | 识别 `0x74727565`（“true”） | `TrueTypeFont`，影响 `intro-数科.ofd` |
| P0 | 识别裸 CFF（`0x01000402`/`0x01000403`） | `TrueTypeFont`，影响 `intro-数科.ofd`、`signout.ofd` |
| P1 | CFF 分支补越界检查 | `TrueTypeFont` |
| P2 | `hmtx` advanceWidth 兜底步进 | `TrueTypeFont`、`AWTMaker` |
| — | CFF2 支持 | 不做（本期范围外） |

## 5. 模块迁移设计

### 5.1 目标

字体解析实现迁入 `ofdrw-font`，`ofdrw-converter` 直接使用其能力。

### 5.2 当前依赖关系

```
ofdrw-gv（无依赖）
 ├── ofdrw-core
 ├── ofdrw-font      ← 仅依赖 ofdrw-gv、commons-io
 ├── ofdrw-reader
 └── ofdrw-converter ← 依赖 fontbox、iText、batik、ujmp
```

`ofdrw-converter` 当前**不依赖** `ofdrw-font`；`ofdrw-font` 被 `ofdrw-layout`、`ofdrw-full` 依赖。

### 5.3 迁移方案对比

#### 方案 A：保留原包名，实现在 ofdrw-font（推荐）

- `ofdrw-font` 中新增包 `org.ofdrw.converter.font`（保留原包名）
- `ofdrw-converter` 删除同名源文件，新增对 `ofdrw-font` 的依赖
- `ofdrw-font` 新增 `fontbox`、`slf4j-api` 依赖

| 维度 | 评价 |
| --- | --- |
| API 变化 | **零**（全限定名完全不变） |
| 适配代码 | **零** |
| 字段可见性改动 | **零** |
| 下游影响 | 依赖 `ofdrw-layout` 的项目会间接引入 fontbox |
| 架构代价 | 包名与模块归属不一致 |

#### 方案 B：新包名 + converter 侧壳类（extends）

- `ofdrw-font` 使用新包名 `org.ofdrw.font.parse`
- `ofdrw-converter` 中每个类改为 `extends` 新实现并重写跨类型方法

**技术障碍**：

1. `TrueTypeFont` 的全部内部状态（`numGlyphs`、`glyphOffsets`、`glyphs`、`data`、`cmaps`、`hmt`、`cffFont` 等 10 个字段）均为 `private`，壳类无法访问，必须改为 `protected`。
2. `parse(TTFDataStream)` 的入参是旧类型，而 `MemoryTTFDataStream extends TTFDataStream` 已占用继承位，`TTFDataStream` 是 abstract class，无法同时继承新类型。
3. `CmapSubtable[]`、`GlyphData[]` 等容器型返回类型无法靠继承解决，必须逐项转换。
4. `GlyphDataProvider`、`FontDrawPathProvider` 为 `@FunctionalInterface`，改成 extends 会影响 lambda 兼容性。

| 维度 | 评价 |
| --- | --- |
| API 变化 | 需额外保证（易遗漏） |
| 适配代码 | 约 20 个类 |
| 字段可见性改动 | 需放开 10 个字段 |
| 下游影响 | 同方案 A |
| 架构代价 | 类型体系出现两套并行语义，维护成本高 |

#### 方案 C：不迁移，仅修复

修复集中在 `org.ofdrw.converter.font` 包内，`AWTMaker` 仅调用接口。

| 维度 | 评价 |
| --- | --- |
| 风险 | 最低 |
| 依赖树变化 | 无 |
| 是否满足“字体处理在 font 模块” | 否 |

### 5.4 方案对比结论

若必须迁移到 `ofdrw-font`，**方案 A 是唯一能以零 API 风险、零适配代码落地的方式**。方案 B 需要改动内部封装且难以保证 API 完全不变，与“所有开放 API 都不能删减和调整参数”的约束存在冲突。

### 5.5 待决问题

1. 是否接受 `ofdrw-font` 中出现 `org.ofdrw.converter.font` 包名（方案 A 的架构代价）。
2. 是否接受依赖 `ofdrw-layout` 的项目间接引入 `fontbox`（方案 A/B 的共同代价）。
3. 若选择方案 C，`ofdrw-font` 保持轻量，但“字体处理在 font 模块”的目标不达成。

## 7. 日志规范化

### 7.1 问题

代码中大量使用 `System.out` / `System.err` 输出告警，存在以下问题：

- 无法通过日志框架统一收集、过滤与落盘，生产环境易丢失
- 无法按级别控制，调试信息与错误信息混杂
- 输出格式不统一，部分带人为前缀（如 `>>`、`警告: `）

### 7.2 排查结果

全仓库有效的 `System.out/err` 输出共 9 处（已注释的不计）：

| 模块 | 文件:行 | 内容 | 处理 |
| --- | --- | --- | --- |
| layout | `AnnotationRender.java:108` | 注解渲染异常信息 | `logger.warn` |
| layout | `VirtualPage.java:95` | 虚拟页面不支持浮动属性 | `logger.warn` |
| layout | `OFDDoc.java:606` | 无法解析 Attachments.xml | `logger.warn` |
| layout | `CellContentDrawer.java:174` | 表格文本与宽度（调试） | `logger.debug` |
| layout | `CellContentDrawer.java:247` | 图片宽高（调试） | `logger.debug` |
| font | `EnvFont.java:156` | 加载字体文件失败 | `logger.warn` |
| converter | `ItextMaker.java:719` | 图片资源解析失败 | `logger.warn` |
| converter | `HtmlMaker.java:156` | 没有设置输出路径 | `logger.warn` |
| converter | `TrueTypeFont.java:317` | CFF 取字形失败 | `logger.warn` |

### 7.3 决策

| 决策点 | 结论 |
| --- | --- |
| 改造范围 | `ofdrw-layout`、`ofdrw-font`、`ofdrw-converter` 三个模块全部改造 |
| 调试输出 | `CellContentDrawer` 的 2 处 `System.out` 降为 `logger.debug` |
| 异常与能力提示 | 全部为 `logger.warn` |
| 版本管理 | `slf4j-api` 在父 POM `dependencyManagement` 统一声明 |

### 7.4 依赖影响

`ofdrw-layout` 与 `ofdrw-font` 当前**没有任何 slf4j 依赖**，改造后需新增：

| 模块 | 新增依赖 | 说明 |
| --- | --- | --- |
| `ofdrw-font` | `fontbox`、`slf4j-api` | 迁移字体解析的必需依赖 |
| `ofdrw-layout` | `slf4j-api` | 仅日志使用 |

`slf4j-api` 不标记 `optional`，作为传递依赖进入下游。使用方需自行提供日志实现（如 `log4j-slf4j-impl`、`logback-classic`）；未提供时 slf4j 会打印一次提示并静默丢弃日志，不影响功能。

### 7.5 父 POM 统一版本管理

父 POM 的 `dependencyManagement` 新增，版本以属性形式声明：

| 依赖 | 版本 | 依据 |
| --- | --- | --- |
| `fontbox` | `2.0.27` | 沿用 `ofdrw-converter` 现有版本，与 PDFBox 主版本保持一致 |
| `slf4j-api` | `1.7.36` | 沿用现有仓库中实际使用的版本 |

各模块引用时不写版本号，避免多模块版本漂移。

## 8. 验证方案

### 8.1 构建环境限制

当前环境 `~/.m2` 为只读文件系统，Maven 无法完成 `install`，`test-compile` 亦因依赖解析失败受阻。因此完整构建验证需在可写环境中进行。

### 8.2 验证手段

| 手段 | 内容 | 目的 | 是否入库 |
| --- | --- | --- | --- |
| 公开 API 兼容性回归测试 | 编译期引用全部签名 + 运行期断言关键行为 | 保证 API 未删减、未调整参数 | 是 |
| 现有测试套件 | 全量 `mvn test` | 保证既有行为不回归 | 是 |
| 本地像素比对 | 与 `ofdrw-viewer-cli` 输出逐页比对 | 保证渲染质量达到参考实现水平 | **否，仅本地执行** |

### 8.3 本地像素比对设计

**参考基准**：`ofdrw-viewer-cli`（已全局安装），它基于 `ofdrw-viewer-engine` 渲染，代表目标实现水平。

```bash
# 生成参考图（96 DPI，全部页面）
ofdrw-viewer-cli <input.ofd> -o <refDir> -d 96
# 输出命名：<refDir>/<stem>-p<NNN>.png
```

**样本与位置**：

| 项 | 内容 |
| --- | --- |
| 样本来源 | 工作区 `ofd_pdf_match/` 下的 58 组 OFD（配套 PDF 仅用于人工交叉核对） |
| 参考图 | `.local_compare/ref/<文档名>/`，共 59 个目录、254 张图 |
| 待测图 | 由 `CanvasImageExporter` / 改造后的 `ImageExporter` 按 `ppm` 对应 DPI 导出 |
| 版本控制 | 样本与图片均**不入库**，已在 `.gitignore` 排除 |

**比对参数对齐**：

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| DPI | 96 | 与 CLI 默认一致，对应 `ppm = 96 / 25.4 ≈ 3.7795` |
| 格式 | PNG | 无损，避免编码差异干扰 |
| 背景 | 白色 | 与 CLI 默认一致 |
| 页面范围 | 全部 | — |

**判定标准**：

| 结果 | 含义 |
| --- | --- |
| 差异像素比例 = 0 | 完全一致 |
| 0 < 比例 ≤ 0.5% | 可接受，需确认差异仅在抗锯齿边缘 |
| 比例 > 0.5% | 需逐项定位原因 |

**预期变化白名单**（这些改动本身会改变渲染结果，需单独确认而非视为回归）：

- GID 失效时改为跳过字形（§4.1）：字体被替换的文档会少字
- GID 越界时跳过单个字形（§4.2）：残缺文档可能少个别字形
- `hmtx` 步进兜底（§4.7 P2）：`DeltaX` 缺失的文档字符间距会变化

**重点观察样本**（覆盖本次修复的各类风险）：

| 文档 | 覆盖场景 |
| --- | --- |
| `intro-数科.ofd` | “true” sfnt、裸 CFF 0402/0403、标准 sfnt 混合 |
| `signout.ofd` | 裸 CFF（MinionPro-Regular） |
| `doc1File.ofd` | 缺 cmap 的 `.otf`，按 GID 渲染 |
| `zsbk.ofd` | 多字体 + 缺 cmap + 签章 |
| `文字横向-数科.ofd` | 缺 cmap + 竖排 |
| `manual.ofd` | 89 页大文档，性能与稳定性 |
| `透明度文字.ofd` | 文字透明度 |
| `containsJPEG.ofd` | JPEG 图像资源 |
